# Mission follow-up in daily guidance — direction for review

Status: proposed direction; no architectural spec, implementation plan or runtime approval is claimed. Prepared on 2026-10-19 against main `acf7f48` for [B07.5-B2](../../../MASTER_PLAN.md). The approved Barrio Home implementation already exists; this is a separate addition to that behavior.

## Intended outcome

Help a learner find useful phrase practice after a mission, without searching for its completion screen. The master plan requires personalized follow-up without duplicate learning events, hint penalties or unrelated scheduling changes. The recommendation below assumes the first increment should be a small optional self-check, available alongside the existing daily activity. Owner review can correct that assumption before the written architecture is prepared.

Success means that a learner can recognize the source of the suggestion, practice its actual phrases, return safely and resume the same saved daily plan. It does not mean a generated score, daily credit, mastery award or permanent history of follow-up completion. This package proposes the direction and work bundles; it supplies no new simulator acceptance evidence.

| ------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **A — Recommended: optional guidance from the current completed mission** | A small “Practice phrases from your mission” entry opens cue/reveal practice for the incorrect-answer source cards recorded in that exact run. Daily plan and Study remain as they are. | Reuses the existing non-assessed follow-up behavior. Reopening starts at the first hidden answer; there is no saved “already practiced” status or permanent dismissal. The entry can remain available until the run is replaced or becomes ineligible. |

A connects recorded difficulty to a concrete action with the fewest new state rules. B can follow if learner observations show that repeated optional suggestions are confusing. Neither direction requires the separately proposed practice passport, assessed voice or downloadable audio packs.

## Recommended behavior

**Suggestion and priority.** Preserve the Home primary action, exact unfinished plan, completed-today state, daily limits and seven-day catch-up behavior. Add one optional secondary entry below the primary activity in both Classic and Barrio, styled with their existing controls. This is an explicitly proposed additive change to Classic Home; the existing approved Home work does not authorize it. Do not move existing tools, replace a recommendation or claim the extra practice fits inside the saved 3/5/10-minute plan estimate. Explain that it is optional extra practice without an invented duration.

**Eligible source.** Select a completed, valid current run for an exactly available, accepted mission/content identity, with at least one still-valid source phrase in `reviewCardIds`. If multiple missions qualify, choose one deterministically by latest run update, then stable mission ID; do not present a stack of competing recommendations. Only recorded incorrect answers populate this list today. A hint, transcript reveal or model answer alone does not become a mistake or lower a score. Say “from your mission,” rather than claiming why each phrase was difficult, how often it was missed, or that every required mission response was correct.

**Exact handoff.** The future architecture must bind a selection to mission ID, content version and run ID. Revalidate source run/content/cards at the actual press and on return from background; a newer run must not silently inherit the old suggestion. Open a read-only follow-up owner, using the existing cue/reveal component, rather than navigating to the current `MissionPreview` route and accidentally starting/restarting a mission. Reveal, Next and Return keep their existing self-check meanings. Cold reopening starts at the first hidden phrase. Returning preserves the original plan identity and remaining queue, and produces no synthetic attempt or completion event.

**Unavailable and failed reads.** Missing source cards are omitted; a source whose authored phrase identity has changed is unavailable until exact content eligibility can be established. Hide an empty suggestion. A restarted/incomplete run, changed version or withdrawn accepted pack invalidates the old handoff. A failed read gives a small scoped retry for guidance and suppresses stale phrase assertions, while independently working Home controls remain available. No replacement plan, mission start, backup write or automatic corrective operation is a read-retry side effect.

**No new progress record in A.** The existing follow-up position/reveal state is local UI state. This proposal deliberately does not persist dismissal, completion, a new storage key, raw answers, reward receipts or telemetry. It therefore must not say “all caught up,” remove a mistake from the historical run, or promise that practiced phrases will stop being suggested. Reads, repeated opens and theme/language changes do not change events, SRS, daily/new/streak counters or mission checkpoints. Backup restore may explicitly replace those sections; guidance must revalidate the restored source and add no mutation beyond that restored state. If durable suppression becomes a requirement, choose B or revise the direction before writing the spec.

## Source facts and the production boundary

- [Mission engine](../../../src/missions/engine.ts): only `event.outcome === 'incorrect'` appends the unique card ID to `reviewCardIds`. Aggregate `assisted` is sticky; node hint/model fields reset during advancement. It is unsuitable for reconstructing per-card reasons or exact historical assistance totals.
- [Mission storage](../../../src/storage/missions.ts): a new run replaces the prior run for that mission. This is a current-run suggestion, not permanent difficulty history. The existing durable coordinator should supply a consistent validated snapshot; implementation must not trust a Home render snapshot as current at press time.
- [Existing completion handoff](../../../src/screens/MissionScreen.tsx) and [self-check component](../../../src/components/MissionFollowUp.tsx): completion resolves source IDs against current cards; the self-check has local reveal/index state and no storage/grading API. A new Home handoff needs stricter exact identity checks and its own read-only owner; the current route has development availability/start behavior.
- [Daily response availability](../../../src/missions/dailyResponse.ts) is currently controlled by the development flag, not an accepted-content registry. [Recommended plan creation](../../../src/storage/recommendedPlan.ts) already preserves an unfinished plan or today's completed plan; [plan schema](../../../src/storage/dailyPlanSchema.ts) has only review/applied/complete phases. A must preserve these contracts.
- The [exact café packet](../../editorial/first-morning-mission-draft.json) is `unreviewed-draft`; the [editorial ledger](../../editorial/review-ledger.json) has no acceptance records. Source-card inventory is not acceptance of the composed mission. There is no identified production accepted-mission resolver to reuse as if it already existed.

The written spec must define an explicit fail-closed eligibility seam tied to the exact authored mission/version/fingerprint and source-card content, with no eligible production entry until genuine review supplies that identity. Numeric version alone is insufficient if bytes can change without a bump. Imported current runs are local practice history, not independent proof of achievement. A development-only labeled fixture can exercise eligible/ineligible/stale cases without claiming content acceptance; a release build must not fall back to that fixture or enable the current draft because the technical tests pass. Acceptance withdrawal must disable future handoffs safely. No accepted dialogue or successful practical-outcome claim is supplied here.

Using a wrong answer once must never create a second learning event merely because Home suggests it. Simulator tests can prove UI/state behavior; actual learners determine whether this guidance is useful or repetitive.
