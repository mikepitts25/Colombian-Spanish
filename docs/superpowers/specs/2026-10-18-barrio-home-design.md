# Barrio-only plan-first Home

Status: owner approved this written specification in this chat on 2026-10-18. The owner approved the [composition proposal](../../design/2026-10-18-barrio-home/README.md) in this chat on 2026-10-18. That approves this writing stage, not runtime implementation. Written-spec approval is recorded; implementation-plan review/execution choice follows. Classic remains default and permanently available.

## Intent and success

Make the next useful practice action obvious without presenting the whole library as today's required work. Preserve the owner's familiar Classic Home while making Barrio a complete optional composition in Light/Dark/System. The owner selected the plan-first approach: current action, quieter activity context, word of the day, then practice/discovery and due decks. Do not turn a visual refresh into new learning/storage behavior or unlock editorial drafts.

Success means a learner can identify the current action, resume the exact retained plan, recover a failed read/start, and find every existing tool in either language at narrow/default/maximum text. All current Classic content, icons, callbacks and route semantics remain. Improved motivation and learning effectiveness require the separate learner pilot; attractive boards or green tests cannot establish them.

## Scope and non-goals

Implement only Barrio Home presentation, a pure presentation selector, additive Home translations and focused integration/native tests. Keep existing recommendation, queue, grade, timing, recovery, theme preference, backup and navigation contracts. No new dependency, account, content release, recording, reward, proficiency badge, collection, storage key or schema. No changes to Mission, Progress, Explore composition, tabs or the Android license/signing/security gates.

Use the two [proposal boards](../../design/2026-10-18-barrio-home/home-composition.png) as composition references, not fixed measurements or final data. The [state board](../../design/2026-10-18-barrio-home/plan-states.png) includes explanatory notes, not product strings. This spec supplies the required behavior and exact new copy below. The large-text study is schematic; native validation must establish actual reflow.

## Current behavior that must survive

`HomeScreen` owns focused/foreground/minute reads via `useFocusedAsync`, fresh budget reloads, the `starting` ref, pending UI state, read retry, start failure, recommendation/calibration, date-seeded word and navigation callbacks. Keep that owner mounted across changes of theme, appearance, language and font size.

`startPlan` reloads and calls `openRecommendedPlan(SHOW_REVIEW_TOOLS)`, then routes the returned current identity to Study or DailyPlan. `startStudy` performs the existing fresh-budget/recommendation checks and bounded direct Study handoff. `openRecommendedPlan` retains an unfinished plan across days and a completed plan for its own local day. Existing transactions determine what actually starts; the presentation is not a second state machine that writes a plan.

Preserve the current fresh production fallback: when there is neither a persisted plan nor an available authored response, the primary callback uses bounded `startStudy`, not a newly introduced durable-plan transaction. Its normal Study resume behavior remains owned by Study. An ordinary saved Study session does not become a `DailyPlan` just to draw a phase strip. When a plan or available response exists, retain the `startPlan` path. A current completed-plan action also uses that existing fresh revalidation. A changed day between render and press may therefore select the fresh next practice through the existing controller rather than open stale completion.

`availableDailyResponse` returns no draft in production. Its actual development activity is one authored greeting, not the full café mission. `DailyPlanScreen` already handles a missing/changed/unavailable linked response with an unavailable message and explicit End/Home. Home must not erase it, create a replacement, navigate directly into Mission or imply it remains playable.

## Architecture and files

1. **`src/utils/homePresentation.ts`**: a pure `deriveHomePresentation(input)` function returning the discriminated plan-card model described below. Inputs are already-read Home facts; it performs no IO, time reads, translation, navigation or mutation. Use the existing typed recommendation/plan objects rather than reconstructing storage envelopes. Export only the input/result types and function needed by Home/tests.
2. **`src/components/BarrioHomeContent.tsx`**: presentational scroll content with typed model/data/callback props. Uses `useAppTheme`, `useThemedStyles`, `ThemedPressable`, `controlSurface`/`controlText` and existing `ThemeIcon` where an icon exists. It may own visual measurements, never learning/start state. Labels plus ordinary vector/line decoration suffice for tools that lack an existing icon; do not add a competing icon system.
3. **`src/screens/HomeScreen.tsx`**: preserve all hooks/controller state above the theme branch and existing Classic JSX/styles. After the existing provider-ready handling, render Barrio content only for `theme.id === 'barrio'`; otherwise retain the current Classic render. Extract shared types or callback adapters only where required; avoid unrelated refactors. No theme-dependent screen key or conditional hooks.
4. **`src/i18n/translations.ts`**: additive `home.barrio.*` keys below; reuse existing strings for shared routes, loading, retry, measured-pace disclosure, catch-up and development tool names. Do not rewrite Classic strings.
5. **Tests**: new `__tests__/utils/homePresentation.test.ts` and `__tests__/components/BarrioHomeContent.test.tsx`; extend HomeScreen and the real DeckProvider/Study harness in `__tests__/screens/HomeWorkload.integration.test.tsx`. Use `__tests__/screens/DailyPlanLifecycle.test.tsx` for the existing linked-player/unavailable recovery behavior; it uses real storage with a mocked deck hook and is not a real-provider Home integration harness. Do not describe hook mocks as provider evidence. Add pure/real-controller coverage as described below.

Include the small original cup as `assets/theme-icons/barrio-cup.png` (128×128 transparent raster), with its editable `barrio-cup.svg` and provenance beside it. Render with the already available external renderer; add no art package to the app. Display at 40×40 points, tinted through the existing accent role like the icon assets; mark decorative/hidden from accessibility. Hide it at fontScale ≥1.4 or available content width below 320 points. It conveys no location, lesson or progress. Do not ship the board SVG/PNG as a screen image.

## Presentation model and precedence

Inputs: provider readiness; focused read `loaded`/`error`; captured `now`; optional validated `DailyPlan`; optional available daily response; recommendation and its deck; `studyStarting`/`studyStartError`; actual deck/card totals, remaining daily new allowance, daily count/target, streak/freezes, word and due-deck data. Home computes these as today. Include whether a persisted applied identity matches the available response's ID/contentVersion. Do not infer availability from a nonempty mission ID alone.

Result has a `kind` of `loading`, `readError`, `reviewResume`, `appliedResume`, `unavailablePlan`, `completedToday`, `recommendation`, `appliedOnly`, or `browse`; one primary action discriminator (`none`, `retryRead`, `existingStart`, `browse`), optional Manage-plan availability, phase rows and only known counts/estimate values. Pending/start-error are overlays on the underlying known model, not new plan identities. Derive in this order:

| Priority | Condition                                                               | Rendering/action                                                                                                                                                                                                                                         |
| -------- | ----------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 1        | Provider not ready or first read not loaded, with no read error         | Loading card; disabled primary. Hide unconfirmed activity counts. Keep the root/provider and callback owner mounted. Provider-not-ready handling may keep the existing whole-screen loader.                                                              |
| 2        | Current read error, including a failed refresh after previous success   | Read-failure heading/body and Try again. Hide stale activity totals/plan assertions; retry only increments the existing read attempt. Independent library browsing remains available once decks are ready.                                               |
| 3        | Persisted review phase                                                  | Resume exact queue, even from an older local day. Remaining count is `review.session.queue.cardIds.length`; never the recommendation or `initialCardIds.length`. Show Manage plan.                                                                       |
| 4        | Persisted applied phase with matching available response                | Resume linked greeting; show development-draft label and Manage plan. Include a completed review row only if this stored plan actually has a review segment whose remaining queue is empty. Applied-only plans have one phase.                           |
| 5        | Persisted applied phase without matching available response             | Show saved-plan unavailable explanation and Open saved plan. Existing start callback revalidates and opens DailyPlan's safe unavailable/End/Home route; never replace, clear or claim playable content. Show Manage plan.                                |
| 6        | Persisted complete phase whose `day` equals local day at captured `now` | Completed heading; View completed plan. No new required work/phase, reward or mastery claim. Optional tools/decks remain.                                                                                                                                |
| 7        | Eligible fresh recommendation with its real deck                        | Show selected count and estimated review minutes; current start callback. New-card summary only if recommendation.newCount is positive. Catch-up explanation only when `recommendation.catchUp`; it does not erase due totals or claim all backlog fits. |
| 8        | No review recommendation, but an available development response         | One greeting-only draft phase and current start callback. No fake completed review or “no learning available” state.                                                                                                                                     |
| 9        | Otherwise                                                               | Browse action. Distinguish empty library, daily new allowance exhausted with new cards present, or nothing due/no eligible new cards. A complete plan from a previous day falls through to fresh eligibility here or above.                              |

While pending, keep the selected card/copy in place, set disabled/busy semantics, replace the CTA label with existing loading text, and block primary/Manage/deck-start actions through the existing guard. Do not disable harmless tab/browse navigation beyond existing application behavior. While a start error is shown, retain the underlying model and display its distinct alert plus Try again; invoke the same existing start action. A read retry and a start retry must never call each other's operation. Existing storage failures remain recoverable without double writes.

Phase rows are static, accessible text, not navigation buttons or a new curriculum. For fresh review, describe review; append a reply phase only when the available response is part of the proposed start. For retained plans, use only actual stored segments. A stored but unavailable future applied segment is labeled Unavailable, not promised as playable. Use text “Current”/“Finished”/“Unavailable” (below), not color/check marks alone. Do not infer assisted/independent performance from a completed phase; Home does not display a proficiency or assistance classification.

## Counts, estimates and activity context

Use locale formatting and singular/plural translations. Fresh review summary uses `recommendation.cardCount` and `recommendation.estimatedMinutes`; identify it as an estimated **review** duration, not the total duration of a multi-phase plan. Keep the existing measured-review/reply disclosure only where the corresponding current values are known and applicable. For saved review show remaining count; omit a new remaining-time estimate rather than manufacture one from the old start budget. For applied resume omit a countdown; a saved 3/5/10-minute preference is not elapsed or remaining time. No estimate calibration or timing changes.

Below the plan card, show actual daily count/target, the existing capped goal track, numeric streak and available freezes with explicit names. Count is recorded study activity, not distinct known words. Keep total due, library new count and remaining new allowance separate and labeled; the compact boards omit some context for space, but runtime must retain all three facts. Do not truncate daily count to the target in prose or claim review completion when the daily target is zero. Hide these values on read failure/loading rather than showing initial zeros. Keep the daily-goal and settings destinations through the existing tabs; add no edit controls in the plan hero.

Word of the day remains exactly one deterministic selected card with original front/back and deck attribution. Do not translate stored content or change selection when the interface theme/language changes. The 48-point audio button retains `speakCard(card)`, saved speed and its accessible Listen + phrase label. No extra playback, automatic speech, download, premium badge or authentic-human provenance promise.

## Layout, routes and accessibility

Order: greeting/quiet cup; plan card; daily context; word; Quiz/Difficult Words/Favorites/Phrases plus Explore; due-deck section and Browse all; development previews when enabled. Keep the existing bottom tabs and Settings entry. Favorites goes to `Phrasebook`, not DifficultWords or Flagged. Explore goes to existing `Explore`, whose AddCard/ManageDecks/Favorites/Study entries remain. Flagged stays in the existing editorial path. Due-deck rows retain the existing direct unbounded deck callback, clearly separate from the bounded plan action. Full names wrap; do not silently cut off long deck names. All callbacks come from the existing owner; the content component does not resolve navigation itself.

Use the shipped Barrio surfaces/text/action/border/state roles. Classic retains its flag stripe, greeting glyphs, avatar, tool icons, hierarchy, word audio glyph, deck rows and callbacks. Omit the flag stripe in Barrio, matching the approved composition; keep it exactly in Classic. Do not introduce multicolor hero panels. Text and controls should use existing type/spacing metrics with content-driven height. No new hardcoded color palette. Any new semantic color role requires the existing source/contrast audit to classify and verify it; prefer existing roles.

Default wide layouts can put tools in two columns; narrow widths or fontScale ≥1.4 stack them. Use available width as well as fontScale so a windowed tablet does not inherit a wide grid. At accessibility text sizes, remove cup and any side-by-side summary text; allow the primary label to wrap. No fixed text heights, negative offsets, horizontal carousels or absolute action footer. Keep headings, button content and all lower rows in one normal vertical scroll with safe-area/bottom-tab clearance. Font-size measurement remount, if still required on this iOS runtime, applies only to presentation below the stable controller.

Every action has at least a 48-point target, named role and actual disabled/busy state. Use header semantics for sections, alert semantics for failures, text next to phase status, and a named progress bar with current/max values where a target exists. Decoration is not focusable. Reading order matches visual order. Avoid nested actionable wrappers and duplicate accessible labels. Use no new motion; existing Reduce Motion and tab behavior remain. Real screen-reader announcements/touch comfort remain separately verified rather than inferred from AX presence.

## Verification and acceptance

### Automated requirements

- Pure precedence table covers all nine kinds, error after stale success, prior-day unfinished, current/past completion, zero/singular/plural counts, applied-only, mismatched content version and no production draft. No clock, storage or global theme access inside the selector.
- New UI tests verify exact routes/callbacks and one primary, readable full deck names, conditional rows, loading/error unknown-count hiding, named audio and route entries, disabled pending controls, alert distinctions and both-language rendering. Check underlying presses, not only label presence.
- Real Home/controller tests hold a start promise, change Classic/Barrio/Light/Dark/System/language/font scale, then resolve/reject: same controller/start intent, one operation/navigation, correct retry and no grade/new counter changes. An unrelated render must not call start or create a plan. Preserve existing Classic tests without rebaselining changed behavior away.
- Retained exact queues/plan IDs win over changed preferences/date. Start crossing midnight uses existing fresh revalidation. Missing/changed/production-unavailable applied content follows DailyPlan recovery and never starts a replacement. Completed view and production review-only bounded path preserve current navigation/queue contracts.
- Run relevant focused tests RED→GREEN before production code, full suite, typecheck/lint/format, calendar/data/content validators and existing theme-color audit. Release content gates must stay closed where unreviewed; never regenerate accepted content to make UI tests pass. CI must pass on the candidate and merged main.

### Native matrix for this Home change

Use the rebuilt foundation development binary plus current JS only if no native configuration/dependency changes occur; otherwise rebuild. Serve from an isolated checkout with its actual installed source, not a symlink to another Metro root. Keep the old normal Metro and other worktrees intact.

Create or use only freshly installed, explicit-UUID own-container QA phones/actual mini proven by `scripts/simulator_isolation.py` before/after launches. No source/alias operation, simulator cloning or direct storage writes. Fixture setup/restore uses supported app import; capture baseline and final all-eleven logical hashes, actual model/version, exact intentional changes, grade/event counts and cold behavior. Any simulated failures use the established separate harness and are labeled as such.

Verify both languages and Barrio Light/Dark on a narrow phone and actual mini: default and live maximum text; upper primary plus real touch scrolling to every lower section; long deck name; all tool destinations; the existing word-audio entry behavior without an audio-quality claim or a new Home Stop control; completed, exact review resume and development greeting resume; production unavailable/review-only/empty/cap fallback through the appropriate build or explicitly labeled test fixture. Roundtrip to Classic must recover its original composition and stored identity without controller/data loss. Home cold restart must retain all intended plan/queue/prefs state. Screenshot-only or AX-positioned cases are recorded accurately rather than called touch acceptance.

Native acceptance is bounded by exercised matrix. Android tooling agreements, signed production checks, hardware audio/performance, assistive-user/daylight/tap comfort and the learner/cultural/editorial gates remain open. A development flag fixture is not a signed production build. No persistent held-pointer/accent-popup acceptance is inferred from unrelated Home tests.
